# QualiFlow 스펙 — 인박스(오픈소스) ↔ CRM 대시보드

> 목적: 회의에서 나온 **모든 기능을 하나도 버리지 않고** 명세화하되,
> (1) 지금 만드는 **인박스 오픈소스**와 (2) 추후 **CRM 대시보드**로 분리하고,
> 데이터를 지금부터 양쪽이 공유하도록 설계해 인박스가 CRM으로 자연스럽게 확장되게 한다.

---

## 1. 아키텍처 — 소유자 모델 교정

소유자 생각: *"인박스 오픈소스(qualiflow)를 이식한 CRM 대시보드"*.

→ 방향(인박스 = 재사용 가능한 OSS, CRM = 더 큰 제품)은 맞다. 다만 **중첩(nesting)이 아니라 공유(shared core)** 가 정확하다.

```
        ┌─────────────────────────────────────────────┐
        │  core  (도메인 계약 + 데이터 모델)            │   ← 단일 토대
        │  Lead · Thread · Message · Qualification ·   │
        │  Channel · lifecycle · scoring · identity    │
        └───────────────▲───────────────▲─────────────┘
                        │               │
            ┌───────────┴────┐   ┌──────┴───────────────┐
            │ 채널 어댑터     │   │  표면(surfaces)        │
            │ alibaba/tg/... │   │  · 인박스 (지금, OSS)  │
            └────────────────┘   │  · CRM 대시보드 (나중) │
                                 └──────────────────────┘
```

- **인박스는 CRM "안에 들어가는" 게 아니라, 둘이 같은 core/데이터를 공유하는 형제다.** 인박스가 첫 표면, CRM이 추가 표면. (Chatwoot이 인박스 OSS이고 그 위에 CRM을 얹는 구조와 동일.)
- 핵심 데이터 뼈대: **Lead = 채널을 가로지르는 정체성(identity).** 한 사람 = 알리바바 + 왓츠앱 + 링크드인. Thread/채널 연락처가 Lead에 링크된다. 이게 회의의 "한 채널 lead를 다른 채널로 확장(노드 연결)"을 가능하게 하는 토대다.

왜 중첩이 아닌가: 인박스 패키지를 CRM 앱 *안에* 물리적으로 넣으면 데이터 모델이 중복되거나 의존성이 꼬인다. 대신 `core`의 Lead/Thread/Message가 **둘이 공유하는 계약**이고, CRM은 core에 필드/엔티티(파이프라인·스코어링)를 더하고 새 뷰를 얹어 "확장"한다.

## 2. 스코프 분리

### 2-A. 인박스 (지금 · 오픈소스 MVP)
- 다채널 메시지 **통합 인박스** (alibaba/telegram/instagram/whatsapp) — *진행 중*
- 채널별 **읽기(추출기)** + **답장(전송)**
- **팔로업 상태**: 내가 응답해야 하나 / 읽음·안읽음 (카톡 읽음 표시류) — *회의 우선순위 3*
- 채널 통합 모듈의 **기본 수집 모듈**: "고객이 응답했을 때" — *우선순위 4의 기본모듈*

### 2-B. CRM 대시보드 (나중 · 같은 core 위)
- Lead **라이프사이클 파이프라인** New → MQL → SAL → SQL — *회의 2 / 우선순위 2*
- **Lead Scoring** (가중 축 합산) — *우선순위 5*
- **통합 대시보드 뷰** — *우선순위 6*
- **Lead Search 자동화** — *우선순위 7*
- **엑셀형 Grade 테이블 뷰** — *우선순위 8*
- **고객 반응 타임라인 → 액션플랜 탭** — *우선순위 9*
- **노드 연결 GUI** (lemlist 참고, 드래그앤드롭 채널 확장, 소스 채널 드롭다운) — *회의 1·3·4 / 우선순위 4의 노코드 GUI*
- **채널 전환 자동화** (알리바바 수취 → Get Contact 자동 → 자동 통합) — *채널 통합*
- **LLM 인콰이어리 파싱** → JSON → 연락처 자동 통합 — *채널 통합*
- **수동 통합** 3케이스 — *수동 통합*

### 2-C. "지금" 설계해 둘 데이터 다리 (양쪽 공유 — 인박스가 채워두기만)
- `Lead` = 채널 가로지르는 정체성 + 채널별 Thread/Identity 링크
- `Lead.lifecycleStage` (파이프라인) — 인박스는 안 써도 **필드는 존재**
- `Lead.scoring` (placeholder)
- `Thread.followUp` (응답 필요 여부 / 읽음 상태)

이걸 지금 스키마·계약에 넣어두면, CRM은 **읽기/쓰기 로직만 추가**하면 된다(데이터 마이그레이션 불필요).

## 4. 소유자가 결정해야 할 것 (경계 — 코드 전에 합의)

아래는 **공개 계약·데이터 모델·비즈니스 규칙**이라 에이전트가 임의로 못 박는다. 합의되면 그때 구현한다.

1. **라이프사이클 enum 정본.** 현재 `core`의 `LeadLifecycleStage`(new/contacted/qualified/sample_requested/sample_sent/negotiating/won/lost/archived)와 회의의 New / MQL(Qualification·NeedAnalysis·GetContact) / SAL(DirectContact·Proposal) / SQL(Order·SecondOrder)이 **서로 다르다.** → 정본을 정해야 함.
   - *제안*: 상위 `stage` = New/MQL/SAL/SQL, 하위 `subStage` = 위 세부. 기존 enum은 폐기 또는 매핑.
2. **Lead Scoring 모델.** 축(예: 거래규모·응답속도·국가·RFQ 수…) 목록과 가중치 합산 규칙.
3. **채널 전환 자동화 규칙.** "알리바바 수취 → Get Contact 자동 변경 → 자동 통합"의 정확한 트리거/조건.
4. **크로스채널 정체성(identity) 모델.** 한 사람 = 여러 채널을 무엇으로 링크하나(자동 매칭 키 vs 수동 링크). 인박스 MVP는 채널별로 분리 저장만 해도 되지만, **링크용 외래키 자리는 지금 비워서라도 만들어 둬야** 확장됨.
5. **팔로업 상태값 정의.** 어떤 상태들(예: needs_my_reply / waiting_on_customer / done)인지.

## 5. 빌드 순서 제안

1. **(지금) 인박스 마무리** — 추출기(F2) 검증 + 답장(F3) + 팔로업(F4) + **DB 영속화**(현재 메모리/파일 → Supabase). 이때 Lead/Thread를 **identity·lifecycle·scoring 필드 포함**해 스키마에 (4번 합의 후).
2. **데이터 다리 고정** — Lead 정체성 + 확장 필드를 core/스키마에 박아 둠(인박스가 채우는 건 메시징 부분만).
3. **CRM 표면** — 파이프라인(F6) → 테이블뷰(F10) → 스코어링(F7) → 노드연결 GUI(F12) → 타임라인(F11) → 자동통합(F13·F14) → 수동통합(F15).

---

## 6. 오픈소스 경계

- **인박스 패키지(OSS 공개 대상)**: `packages/core`, `packages/adapter-*`, 인박스 UI. 채널 통합 + 통합 인박스 + 답장 + 팔로업.
- **CRM 대시보드(별도/상위 제품)**: 위 core를 의존성으로 가져와 파이프라인·스코어링·노드GUI·자동화를 얹음. 인박스를 "이식"하는 게 아니라 **core를 공유**한다.
