# QualiFlow CRM — 기술 학습 가이드

## 머리말

이 프로젝트는 "실시간 메신저 채널을 읽어 들이는 엔진(QualiFlow, 이하 qf)"과 "그 데이터를 화면으로 보여주는 바이어 CRM 제품(buyer-pool-dashboard, 이하 bpd)" 두 레포로 이루어져 있어서, **현대 웹 풀스택의 거의 모든 층**(서버/클라이언트 컴포넌트, Postgres 스키마와 보안, 로컬 자동화 에이전트, 모노레포 아키텍처)을 **하나의 실제 동작하는 코드베이스 안에서** 비교하며 배울 수 있습니다. 특히 같은 개념(병렬 데이터 로딩, 멱등성, 토큰 인증)이 여러 자리에서 반복 등장하기 때문에, 한 번 이해하면 곧바로 다른 파일에서 "아, 여기도 같은 패턴이구나"를 확인하며 학습이 굳어집니다. 책으로 추상 개념을 외우는 대신, **실제 파일을 열어 console.log를 찍고 한 줄을 지워보며** 체감하는 방식으로 설계된 가이드입니다.

권장 순서는 "눈에 보이는 것 → 데이터가 저장되는 곳 → 데이터가 들어오는 곳 → 전체를 묶는 뼈대" 입니다.

### async 서버 컴포넌트 + Promise.all 병렬 로딩 + `dynamic = 'force-dynamic'`
🟡 **중급**

- **우리 코드에서**: `src/app/page.tsx:6,9-13` (`export const dynamic = "force-dynamic"` + `Promise.all`로 3개 쿼리 동시 실행). 더 큰 예: `src/app/(demo)/messenger/page.tsx:21,34-41`
- **왜 중요**: 서버 컴포넌트 함수에 `async`를 붙이면 렌더 전에 데이터를 기다릴 수 있습니다. `Promise.all([...])`로 독립적인 쿼리 3개를 '순차'가 아니라 '동시에' 던져 첫 페인트를 빠르게 합니다. `force-dynamic`은 '이 페이지는 매 요청마다 새로 그려라(캐시·정적화 금지)'는 뜻 — 항상 최신 CRM 데이터를 보여주려고 켭니다.
- **어떻게 익히나**: `page.tsx`의 `Promise.all`을 `await` 3줄로 풀어 쓴 뒤 네트워크 탭에서 로딩이 느려지는지 비교하세요. `dynamic` 줄을 지우면 빌드 시 정적 캐시되어 데이터가 안 바뀌는 현상을 재현해 보면 `force-dynamic`의 의미가 와닿습니다.

### 접근성 있는 폼: noValidate + aria-invalid/describedby/busy
🟡 **중급**

- **우리 코드에서**: `src/app/dashboard-client.tsx:729-780` (OTP 로그인 폼: `noValidate`, label로 input 감싸기, `aria-invalid`·`aria-describedby`로 에러 연결, `aria-busy` 로딩, `autoComplete="one-time-code"`, `inputMode`). 에러 시 시각 표시: `src/app/globals.css:702-705` (`.field:has(input[aria-invalid="true"])`). 토글 버튼 a11y: `src/components/app-shell/app-sidebar.tsx:77,144`
- **왜 중요**: 폼은 '보이는 모양'만이 아니라 '상태를 보조기술에 전달하는 것'이 중요합니다. `aria-invalid`가 켜지면 스크린리더가 오류를 읽고, `aria-describedby`가 그 input과 에러 문구(id)를 연결합니다. 같은 `aria-invalid` 속성을 CSS `:has()`가 잡아 빨간 테두리까지 입혀(`globals.css:702`) '한 신호로 시각+비시각 둘 다' 처리하는 점이 좋은 설계입니다. `inputMode="numeric"`·`autoComplete="one-time-code"`는 모바일에서 숫자 키패드와 OTP 자동입력을 켜는 실전 디테일입니다.
- **어떻게 익히나**: 로그인 화면에서 빈 이메일로 제출해 `aria-invalid=true`가 붙고 `.field` 테두리가 빨개지는 흐름을 DevTools로 추적하세요. 브라우저 기본 검증을 끄는 `noValidate`를 지우면 커스텀 에러 메시지와 충돌하는 걸 보면 왜 껐는지 이해됩니다. MDN의 ARIA form 패턴 참고.

### const 배열에서 유니온 타입 파생 (`(typeof X)[number]`)
🟡 **중급**

- **우리 코드에서**: `src/lib/types.ts:3-8` (Grade/ViewMode 등을 `GRADES` 등 상수 배열에서 파생), `10-17` (직접 리터럴 유니온), 소비처: `src/app/dashboard-client.tsx:79` (densityOptions), `1067` (`value as BuyerQualification|"all"`)
- **왜 중요**: `"A"|"B"|"C"` 같은 유니온 타입을 손으로도 쓰지만(`line 10-17`), 여기선 한 발 더 나가 `GRADES` 배열 하나를 '단일 출처'로 두고 `(typeof GRADES)[number]`로 타입을 자동 도출합니다(`line 3`). 그러면 select 옵션을 그리는 **런타임 배열**과 **컴파일타임 타입**이 항상 일치 — 한쪽만 고쳐 생기는 버그를 원천 차단합니다. 실무 TS의 핵심 습관입니다.

```ts
const GRADES = ["A", "B", "C"] as const;       // 런타임 배열(=select 옵션)
type Grade = (typeof GRADES)[number];          // "A" | "B" | "C" (컴파일타임 타입)
```

- **어떻게 익히나**: `constants.ts`에서 `GRADES` 배열에 값을 하나 추가하면 Grade 타입과 select 옵션이 동시에 늘어나는지 확인하세요. `as const`가 빠지면 타입이 그냥 `string[]`로 넓어져 파생이 깨지는데, 이를 일부러 재현해 보면 `as const`의 의미가 명확해집니다.

### useSyncExternalStore로 외부 스토어(localStorage) 구독
🔴 **고급**

- **우리 코드에서**: `src/components/app-shell/use-stored-collapse.ts:14-50` (subscribe/getSnapshot/getServerSnapshot 3인자). 같은 패턴 재사용: `src/app/dashboard-client.tsx:2082-2114` (useStoredPreference), `src/features/crm-views/reactions-view.tsx:54-89` (useColWidths), `179-214` (useStoredColumns)
- **왜 중요**: 이 프로젝트의 시그니처 패턴입니다. localStorage는 React 바깥의 '외부 상태'라, 흔히 쓰는 `useEffect`로 읽어 setState하는 방식은 (1) 첫 렌더 후 한 번 깜빡이고 (2) 서버/클라 렌더 결과가 달라 hydration 경고를 냅니다. `useSyncExternalStore`는 subscribe(변경 구독)·getSnapshot(현재값)·getServerSnapshot(SSR 기본값) 3개를 React에 직접 줘서, effect 없이 일관되게 값을 읽고 같은 키를 쓰는 사이드바·AI레일이 즉시 동기화됩니다(line 12, 46의 커스텀 이벤트 dispatch).
- **어떻게 익히나**: `use-stored-collapse.ts`의 주석(5-13줄)을 먼저 읽고, `getServerSnapshot(()=>defaultCollapsed)` 인자를 의도적으로 잘못 줘 hydration mismatch 경고를 재현했다 복구하세요. 같은 훅을 effect+useState 버전으로 직접 다시 짜 깜빡임을 비교하면 '왜 이걸 쓰는지'가 명확해집니다. React 공식문서 `useSyncExternalStore`.

### CSS Grid + `:has()` 부모 선택자로 사이드바 접힘을 JS 없이 처리
🔴 **고급**

### 관계형 스키마 설계 — 테이블·외래키(FK)·on delete 동작
🟢 **입문**

- **우리 코드에서**: `supabase/migrations/0001_initial_schema.sql:33-96` (workspaces→leads→threads→messages 사슬). FK 예: `threads.lead_id references leads(id) on delete cascade` (`0001:66`), `leads.client_id references client_accounts on delete set null` (`0001:36`)
- **왜 중요**: 데이터를 '한 표'가 아니라 여러 표로 쪼개고 표끼리 id로 연결하는 게 관계형 DB의 핵심입니다. FK는 '없는 lead를 가리키는 thread' 같은 깨진 데이터를 DB가 막아주는 안전장치이고, `on delete cascade`(부모 지우면 자식도 같이 삭제) vs `set null`(부모만 끊고 자식은 보존)은 '리드를 지우면 그 대화도 지울까, 남길까' 같은 실제 정책을 한 줄로 박는 자리입니다.
- **어떻게 익히나**: `0001`을 위에서 아래로 읽으며 화살표를 그려보세요: workspace 1개 → lead 여러 개 → thread 여러 개 → message 여러 개(1:N). 그다음 각 FK의 on delete가 cascade인지 set null인지 표시하고 '왜 이걸 골랐을까'를 한 문장씩 적어보면 설계 의도가 보입니다.

### Row Level Security(RLS) — '내 워크스페이스 행만 보인다'를 DB가 강제
🟡 **중급**

- **우리 코드에서**: `0001:242-249` `enable row level security` (8개 테이블), 정책 예: `0001:252-255` read, `0001:289-294` write(`using` + `with check`). 판정 헬퍼: `0001:172-186` `is_workspace_member(...)`
- **왜 중요**: 멀티테넌트(여러 고객사가 한 DB를 공유) 앱에서 '남의 데이터가 안 보이게' 하는 일을 애플리케이션 if문에 맡기면 한 군데만 빠뜨려도 데이터가 샙니다. RLS는 그 규칙을 테이블에 직접 붙여, 어떤 쿼리로 들어오든 로그인 사용자(`auth.uid()`)가 멤버인 워크스페이스 행만 통과시킵니다. `using`(읽기/대상 행 필터)과 `with check`(쓰기 시 새 행 검증)의 구분이 핵심입니다.
- **어떻게 익히나**: `0001`의 정책 한 쌍(read 1개 + write 1개)을 골라 using/with check가 각각 언제 평가되는지 적어보세요. 그다음 `0001:172`의 `is_workspace_member` 함수 본문을 읽고, '이 함수가 false면 그 행은 존재하지 않는 것처럼 사라진다'는 RLS의 기본 동작(기본 deny)을 머릿속에 새기면 됩니다.

### 멱등 upsert — `ON CONFLICT DO NOTHING`으로 '같은 요청 두 번 = 결과 한 번'
🟡 **중급**

- **우리 코드에서**: 유니크 인덱스 정의: `0006_agents_and_message_idempotency.sql:66-67` `messages(workspace_id, channel_id, external_message_id)`. 사용처: `0009:133-146` `insert into messages ... on conflict (...) do nothing` + `if found then v_messages := v_messages + 1`. identity는 `0009:103-109`
- **왜 중요**: 네트워크는 언제든 끊기고 에이전트는 같은 메시지를 재전송할 수 있습니다. **멱등(idempotent)**이란 '몇 번을 보내든 DB 상태가 같음'을 뜻하고, 그래서 재시도가 안전해집니다. UNIQUE 인덱스로 '중복의 정의'를 박고 `ON CONFLICT DO NOTHING`으로 충돌 시 조용히 넘어가며, `found`로 '진짜 새로 들어온 것만' 카운트합니다. 동기화·웹훅·결제 같은 모든 외부 연동의 기본기입니다.
- **어떻게 익히나**: `0006:62-67` 주석을 먼저 읽으세요 — `external_message_id`가 NULL인 행은 서로 다르게 취급된다는 Postgres의 NULL 규칙이 왜 outbound 초안에 유용한지 설명합니다. 그다음 `0009:144`의 `if found`가 없으면 카운트가 어떻게 틀어질지 추적해보면 멱등 카운팅의 미묘함이 잡힙니다.

- **어떻게 익히나**: `admin.ts`의 주석(이중 게이트: `NODE_ENV!=production` AND `QUALIFLOW_DEV_SEED_LOGIN=1`)을 읽고, bpd `client.ts` 맨 위 `server-only`가 무슨 역할인지 Next.js 문서에서 확인하세요. 실험: `NEXT_PUBLIC_` 변수와 일반 변수를 클라이언트 컴포넌트에서 각각 console.log 해 보고 무엇이 보이는지 비교.
